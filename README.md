# k3sctl

Одна программа для нового сервера с k3s: подготовить сервер, поставить k3s
и получить к нему доступ без копирования админского `k3s.yaml` на свою машину.

## Установка

```bash
make install
```

Бинарник `k3sctl` попадает в `$(go env GOPATH)/bin`. Сборка в `build/`:
`make build`.

## Порядок для нового сервера

Сервер здесь назван `zeon`, имя любое.

```bash
k3sctl init zeon          # 1. завести сервер: создаст servers/zeon.env, его нужно заполнить
k3sctl cloud-init zeon    # 2а. записать servers/zeon.cloud-init.yaml для поля cloud-init при создании виртуалки
k3sctl prepare zeon       # 2б. ...или подготовить уже созданный сервер по SSH (под root)
k3sctl install zeon       # 3. поставить k3s (K3S_ROLE в файле: server или agent)
k3sctl access zeon        # 4. завести учётку и записать контекст в ~/.kube/config
k3sctl list               # какие серверы заведены (папка servers/)
```

Команда `k3sctl` без аргументов печатает эту шпаргалку. Имя сервера — это
файл `servers/<имя>.env` в текущей папке: удобно работать из корня этого
репозитория, папка `servers/` в его `.gitignore`. Вместо имени можно дать
путь к файлу настроек.

Файл настроек один на сервер, шаблон с пояснениями:
[internal/config/server.env.tpl](internal/config/server.env.tpl). Секретов
в нём нет, только адреса, имена и пути к ключам. `init` сразу записывает
готовый файл: все переменные активны и заполнены, остаётся вписать
`SSH_HOST`. Что `init` проставляет сам:

- ssh-ключ: ищет в `~/.ssh` в момент `init`, первый найденный из `id_rsa`,
  `id_ed25519`, `id_ecdsa`, публичный к нему `.pub`; если ни одного нет,
  предупреждает, и `SSH_KEY` нужно вписать руками;
- версия k3s: спрашивает у `update.k3s.io` текущую стабильную и записывает
  в `K3S_VERSION`, чтобы версия была зафиксирована, а не «какая будет в день
  установки»; без сети поле остаётся пустым, и `install` возьмёт последнюю;
- пользователь `user`, вход на свежий сервер под `root`, часовой пояс
  `Asia/Almaty`;
- роль k3s `server`; адрес в сертификате и в kubeconfig при запуске берётся
  из `SSH_HOST`, если `K3S_TLS_SAN` и `API_URL` пустые;
- запас процессора и памяти для самой ОС и k3s (`K3S_SYSTEM_RESERVED`):
  по размеру машины, 10 % памяти и 100m на ядро, подам не отдаётся; порог
  выселения подов `K3S_EVICTION_HARD`, когда свободной памяти меньше 5 %
  или диска меньше 10 %;
- штатная остановка подов при перезагрузке или выключении ноды
  (`K3S_SHUTDOWN_GRACE`, 60 с на все поды, из них
  `K3S_SHUTDOWN_GRACE_CRITICAL` 20 с на системные): kubelet задерживает
  выключение и даёт подам завершиться, поды остаются на своей ноде, что
  важно для StatefulSet с local-path томами;
- лимиты логов: системный журнал не больше `JOURNAL_MAX_USE` (500M), логи
  контейнеров `K3S_LOG_MAX_SIZE` × `K3S_LOG_MAX_FILES` (10Mi × 3) на
  контейнер;
- перезагрузка после обновлений по воскресеньям в 04:00 по времени сервера
  (`PREPARE_REBOOT_CRON`, расписание cron), и только если система её
  просит; пусто = не перезагружать автоматически;
- учётка `admin` с ролью `cluster-admin`, имя контекста равно имени сервера.

Команды при запуске ничего не ищут: что записано в файле, то и действует.

### Что делает каждый шаг

**init** создаёт файл настроек: находит ssh-ключ, узнаёт стабильную версию
k3s, подставляет умолчания и имя контекста. На сервер не ходит.

**cloud-init** записывает `servers/zeon.cloud-init.yaml`: пользователь с
sudo и вашим ssh-ключом (плюс ключи из `SSH_EXTRA_PUBKEYS`, если нужно
сразу дать доступ коллеге или положить запасной), запрет входа по паролю, обновление пакетов, лимиты
inotify для агентов логов, часовой пояс, потолок системного журнала,
перезагрузка после обновлений по расписанию. Содержимое файла вставляется в
поле user-data при создании виртуалки (в Hetzner это поле «Cloud config»,
в Yandex Cloud метаданные с ключом `user-data`) **целиком**: первой строкой
должна быть `#cloud-config`, иначе cloud-init молча пропустит весь файл.
Срабатывает один раз при первой загрузке. `SSH_HOST` для этого шага не
нужен, адрес появится после создания.

**prepare** делает то же самое на уже созданном сервере. Заходит по
порядку: `SSH_USER` по ключу (сервер уже подготовлен), `BOOTSTRAP_USER`
по ключу (ключ положил провайдер или cloud-init), `BOOTSTRAP_USER` по
паролю из `BOOTSTRAP_PASSWORD` (`ask` = спросить в терминале, пароль
нигде не сохраняется). Если провайдер дал только адрес и пароль root,
этого достаточно: при входе по паролю `prepare` кладёт ваш ключ и root-у,
а потом закрывает вход по паролю. Дальше выполняет шаги по SSH. Если после обновления пакетов система просит перезагрузку, `prepare`
на свежем сервере (k3s ещё нет) сам перезагружает его, ждёт возвращения и
заново проверяет вход по ключу и sudo (`PREPARE_REBOOT=auto`; `true` —
перезагружать и с k3s, `false` — только предупредить). Дальше обновления
безопасности Ubuntu ставит unattended-upgrades, а перезагружает задание
`/etc/cron.d/k3sctl-reboot` по расписанию `PREPARE_REBOOT_CRON`, если есть
`/var/run/reboot-required`. Запрет паролей пишется в `/etc/ssh/sshd_config.d/00-no-password.conf`:
имя `00-*` читается раньше провайдерского `50-cloud-init.conf`, а у sshd
побеждает первое значение, поэтому правило не слетает после перезагрузки.

**install** ставит k3s официальным установщиком. На любой роли в
`/etc/rancher/k3s/config.yaml` записывается запас ресурсов для системы,
порог выселения подов, чтобы при перегрузке умирали поды, а не ОС с ssh,
лимит логов контейнеров и штатная остановка подов при выключении ноды
(плюс лимит задержки выключения в `/etc/systemd/logind.conf.d/90-k3sctl.conf`).
Master (`K3S_ROLE=server`): туда же адреса из `K3S_TLS_SAN` (по умолчанию
`SSH_HOST`) для сертификата API, пользователю `SSH_USER` выдаётся
`sudo -n kubectl`. Worker (`K3S_ROLE=agent` и `K3S_SERVER_SSH_HOST`): токен
кластера читается с master по SSH и сразу передаётся на worker, на вашу
машину он не сохраняется. Порт 6443 на файрволе откройте только для своих
адресов.

**access** создаёт ServiceAccount `SA_NAMESPACE/SA_NAME` с ролью
`CLUSTER_ROLE`, выпускает токен (бессрочный через секрет, либо на срок
`SA_TOKEN_TTL`, например `8760h`), берёт корневой сертификат кластера из
конфигмапа `kube-root-ca.crt` и записывает кластер, пользователя и контекст
`CONTEXT_NAME` в `LOCAL_KUBECONFIG`. Другие контексты не трогает. В конце
подключается к кластеру и печатает, под кем вошли. Повторный запуск
безопасен: учётка та же, токен обновляется.

Проверка:

```bash
kubectl --context zeon get nodes
```

## Где секреты

- Приватный ssh-ключ остаётся в `~/.ssh`, в файле настроек только путь.
- Токен кластера k3s нигде не хранится, `install` передаёт его с master на
  worker напрямую.
- Токен учётки для kubectl попадает только в `~/.kube/config` с правами
  0600. Потеряли файл: повторите `access`.
- Админский `k3s.yaml` с сервера на вашу машину не копируется.

## Требования

- На Mac: `ssh` (системный, со всеми настройками из `~/.ssh/config`), Go для
  сборки.
- На сервере: Ubuntu/Debian (apt) или Alpine (apk), `curl`, доступ в
  интернет до `get.k3s.io`.

## Устройство

- `cmd/k3sctl` — точка входа; `internal/app` — разбор команд.
- `internal/command` — сами команды.
- `internal/remote` — серверные скрипты на POSIX `sh` и шаблон cloud-init,
  встроенные в бинарник. Скрипт уезжает на сервер по SSH целиком вместе с
  настройками, поэтому на сервере ничего заранее класть не нужно.
- `internal/sshx` — запуск через системный `ssh`.
- `internal/kubecfg` — запись в kubeconfig и проверка доступа через client-go.
- `internal/config` — файлы настроек серверов и шаблон `server.env.tpl`.
