# k3s_config_merge

Скрипты для нового сервера с k3s: подготовить сервер, поставить k3s и
получить к нему доступ без копирования админского `k3s.yaml` на свою машину.

| Скрипт | Что делает |
|---|---|
| `prepare_server.sh` | Готовит свежий сервер: пользователь с sudo и вашим ssh-ключом, запрет входа по паролю, обновление пакетов, sysctl для агентов логов, часовой пояс. Ключ `--print-cloud-init` печатает то же самое в виде user-data для cloud-init. |
| `install_k3s.sh` | Ставит k3s официальным установщиком: master (`server`) или worker (`agent`). |
| `setup_sa_access.sh` | Заводит в кластере учётку (ServiceAccount), получает её токен и записывает контекст в `~/.kube/config`. |

Все три читают настройки из `.env` рядом со скриптами (в git не входит,
образец `.env.example`). Один `.env` описывает один сервер; для другого
сервера передайте `--env-file другой.env`.

## Требования

- На Mac: `ssh`, `kubectl`, bash 3.2 (штатный).
- На сервере: Ubuntu/Debian (apt) или Alpine (apk), `curl`, доступ в
  интернет до `get.k3s.io`.

## Порядок работы

### 1. Подготовить сервер

Вариант А, при создании виртуалки (Yandex Cloud и другие провайдеры с
cloud-init): вставьте результат в поле user-data.

```bash
./prepare_server.sh --print-cloud-init > user-data.yaml
```

Вариант Б, на уже созданном сервере: заходит под `BOOTSTRAP_USER` (обычно
`root` с ключом от провайдера) и делает всё то же по SSH.

```bash
./prepare_server.sh
```

Запрет паролей пишется в `/etc/ssh/sshd_config.d/00-no-password.conf`.
Имя `00-*` читается раньше провайдерского `50-cloud-init.conf`, а у sshd
побеждает первое значение, поэтому правило не слетает после перезагрузки.
Для верности в `/etc/cloud/cloud.cfg.d/` кладётся `ssh_pwauth: false`.

### 2. Поставить k3s

Master: `K3S_ROLE=server`. В сертификат API попадут адреса из `K3S_TLS_SAN`
(по умолчанию `SSH_HOST`), они пишутся в `/etc/rancher/k3s/config.yaml`.
Пользователю `SSH_USER` выдаётся `sudo -n kubectl`.

Worker: `K3S_ROLE=agent` и `K3S_SERVER_SSH_HOST` (SSH-адрес master). Токен
кластера скрипт сам читает с master по SSH, на вашу машину он не
сохраняется. Можно вместо этого задать `K3S_TOKEN` явно.

```bash
./install_k3s.sh
```

Откройте на файрволе порт 6443 только для своих адресов.

### 3. Получить доступ

```bash
./setup_sa_access.sh
```

Создаёт ServiceAccount `SA_NAMESPACE/SA_NAME` с ролью `CLUSTER_ROLE`,
выпускает токен (бессрочный через секрет, либо на срок `SA_TOKEN_TTL`,
например `8760h`), берёт корневой сертификат кластера из конфигмапа
`kube-root-ca.crt` и записывает кластер, пользователя и контекст
`CONTEXT_NAME` в `LOCAL_KUBECONFIG`. Другие контексты не трогает. Повторный
запуск безопасен: учётка та же, токен обновляется.

Проверка:

```bash
kubectl --context my-k3s get nodes
```

## Устройство

Локальные скрипты на bash 3.2, общие функции в `lib/common.sh`. Серверная
часть каждого скрипта лежит в `lib/remote_*.sh`, написана на POSIX `sh` и
передаётся на сервер по SSH целиком вместе с настройками (строки
`ИМЯ='значение'` в начале), поэтому на сервере ничего заранее класть не
нужно.

## Тесты

`./test/run_tests.sh` поднимает docker-контейнер со свежим alpine, sshd и
бинарником k3s, прогоняет все три скрипта и проверяет результат. Подробности
в `CLAUDE.md`.
